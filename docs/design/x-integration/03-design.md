# X RSS 接入实施方案

状态：设计稿，2026-10-24。基于 [上下文](01-context-brief.md)，推荐 [方案 A](02-options.md)。未开始实现。

## 范围

首版支持指定账号的独立帖文，保留原帖 ID、作者、发布时间、文本、引用和外链。配置 30 分钟轮询、首次回溯 7 天作为验证默认值。复用初审、选文、研读、Git 归档和汇报。

首版不承诺完整线程拼接、外链自动入池、多媒体理解、全网搜索、已归档帖自动重研、帖子删除同步。回复和纯转帖优先在 RSSHub 路由中过滤；标准 RSS 缺少类型信息时不靠标题猜测，保留并明确展示来源。

## 架构

```mermaid
flowchart LR
 X[X 账号动态] --> R[独立 RSSHub]
 R --> F[现有 Feed 抓取与 Python 解析]
 F --> N[X 帖子规范化与准入]
 N --> P[内容池与共享初审]
 P --> S[主题选文与深度研究]
 S --> G[GitHub 归档]
 G --> W[既有每日汇报]
```

凭据与 X 接口变化由中间服务承担。选文和研究中的远程内容始终是资料，不成为执行指令。普通 RSS 保持现有规则。

## 一、先验证数据源

1. 记录 RSSHub 固定版本或镜像 digest，依据该版本文档配置 Web Cookie 或开发者 API。示例路由为 `/twitter/user/<username>`，具体过滤参数以实测版本为准。
2. 用 2～3 个账号采样，检查条目 ID、原帖 URL、作者、原始时间、长帖正文是否截断、引用边界、重复抓取是否稳定。
3. 验证错误时返回可识别错误而非“成功空 Feed”；正常空 Feed 与故障不可仅凭条目数量混同。
4. 保存脱敏样本供离线自动化测试。未通过取数验证时不扩展产品界面，也不声称 X 已接入。

中间服务若使用现有可信 HTTPS 地址，可先不改网络访问机制。若在本机部署，必须先完成下面的受信任端点支持，不能通过关闭全部私网检查来跑通。

## 二、来源/API 契约

复用 `capability_id=web_feed`，在 `SourceOptionsSchema` 增加 `feed_content_type: article | x_post`，默认 article。页面新增“X（RSS）”入口，本质创建一个启用 x_post 策略的 Feed 来源。

用户输入 Feed URL 和来源名称；预览展示原帖链接、正文、时间来源和不入池原因。首版直接输入服务生成的 Feed URL，避免把某个 RSSHub 版本的路由构造固化到 UI。

Feed URL 中不放 X Cookie。若实例需要独立访问 Token，使用现有 secrets store 的独立引用字段；不得把密钥放 query 或在日志中输出。该配置是 RSS 服务访问凭据，与 X 登录凭据不同。

`POST /sources`、`PATCH /sources/:id` 复用，Zod 校验来源策略只适用于 web_feed；普通来源拒绝不相关策略。保存策略变化时沿用候选重验机制，已入池数据不批量回写。

## 三、内容转换与元数据

在 Feed 解析之后增加 TS 规范化模块，Python 保持通用解析。补充 Python 输出的“正文来自 content/description/summary”字段，以便判断，而非按长度判断 X 正文完整性。

增加可选结构化 `content_context`：kind、post_id、author_handle、body_origin、completeness_basis、published_at_source。它从 ContentItem 传到正文版本；建议在 `article_revisions` 增加默认 `{}` 的 `content_context_json`，Drizzle schema 和 SQLite 初始化同步修改。初审读取版本元数据，防止后续来源配置变化重新解释旧内容。

规则：

- 只接受精确 X/Twitter 域名及合法 `/.../status/<数字ID>` 原帖链接；从 status ID 得到稳定身份，统一 canonical 为 `https://x.com/i/status/<id>`，保留 original_url 和作者。
- `source_item_id` 使用 `source_id:x:<post_id>`。GUID 只作辅助，不能因中间服务变更 GUID 就新增同一帖子；缺少可验证原帖链接进入待复核。
- HTML 转安全 Markdown，保留正文段落、链接及明确的引用边界；脚本、追踪/装饰头像等不进入正文。可复用现有提取能力，但不发网络请求补抓 X 页面。
- 只在明确选择 x_post 且中间服务样本已证实提供完整内容时，把对应 description/content 当正文；截断、只有链接或无文本进入待复核。Feed 没有可靠完整度标识时明确依赖该服务版本的输出约定，不能自动证明每篇完整。
- 日期保留 `verified:false`，另标 `published_at_source=feed`；x_post 模式接受有效 Feed 原始发布时间，仍拒绝缺失、未来和过期日期。禁止用抓取时间或 updated 时间冒充发布时间。
- 标题采用作者和日期等独立标题，避免整条正文同时作为标题，触发现有“正文等于标题”的空内容判断。
- 有实质文本的短帖可入池，取消仅针对 x_post 的 80 字符门槛；不足现有 16 字符证据要求的短内容标记初审 insufficient，保留但不自动调用 AI。不能拼元数据凑证据。

线程中的一条回复就是一个帖子；引用文字必须保留作者归属。不把引用内容自动归为发帖人观点。首版保留外链，用户需要可另行收录文章；不引入递归抓取。

## 四、准入、幂等与后续 AI

修改 `evaluateContent` 和 `enqueue/drain` 的策略分支：x_post 日期/内容不足进入 review，不走 web_page 自动补抓；只对 x_post 应用独立规则，保留关键词、时间窗和排除条件。

初审使用规范化后的正文和版本元数据，Prompt 标明“社交帖子，可能不包含完整技术上下文”。仍要求正文可核验的证据；有限材料应低置信度或不足，不因来自指定账号就保证价值。

同一帖子多次抓取、多个来源引用，复用 canonical 身份并保存来源关系。首版对已 ready 帖沿用不覆盖规则；修订/编辑追踪明确留待后续，不把反复采集描述为持续更新正文。同步请求和后台轮询仍复用 source 级 active 去重。

选文、研究和发布复用现有机制。成功入池不保证自动产生研报，仍受初审状态、选文预算与研究质量约束。已归档文章跨主题排除规则不在本需求中修改。

## 五、受信任中间服务访问

如需 localhost/内网部署，新增服务端配置的精确端点允许列表：协议、主机、端口和可选路径前缀；默认空。它只允许 Feed 拉取访问管理员配置的服务，不扩展到帖子链接、图片下载、普通网页补抓或 Webhook。

拒绝 URL userinfo；带认证请求禁止跨源重定向。受信任端点首版可直接禁止重定向以减小范围。非允许列表请求保持私网拒绝；检查覆盖回环地址段、IPv6、IPv4-mapped IPv6，DNS 失败关闭请求。域名需要解析并将已检查地址绑定到连接，不能检查后让 fetch 重新解析产生 DNS 重绑定窗口；实现时选用支持显式 lookup/dispatcher 的客户端。

读取响应时按字节累计限制并超限终止，避免当前“先读完整响应再检查”的问题。测试请求不得把例外权限传到任意 item 链接。此部分可独立提交，便于上游审查。

## 六、运行、失败与容量

RSSHub 负责 X 登录失效、上游限流和自身缓存。OpenLore 记录 Feed HTTP/解析错误，不推进成功游标，不生成空内容文章；采用现有轮询恢复，不新增无限即时重试。Feed 时间窗口是有限的，长时间离线可能漏帖；首版不承诺完整历史回补。

预估验证规模 3 个账号、30 分钟轮询，约 144 次 Feed 拉取/天，不等于 X API 请求量。AI 初审按新增帖子发生，验证期应限制来源与回溯窗口，并用低研究预算控制成本。

沿用采集状态、失败原因与 AI 日志；至少可判断 Feed 获取失败、正文不完整、日期无效、已重复、初审不足。日志不输出访问密钥或 Cookie。

Windows 本地验证前，检查 Node/pnpm/Python/uv/Git；如当前 Python runner 无法定位 venv，补 `.venv/Scripts/python.exe` 平台路径并保留 POSIX 行为。中间服务可在现成远端或 Docker/WSL 运行，不能假定本机已有 Docker。

## 七、实施拆分

| 阶段 | 改动 | 完成依据 |
| --- | --- | --- |
| P0 取数验证 | 固定 RSSHub 版本、配置账号、采样；不改应用 | 新帖子与原始字段对应，可持续拉取 |
| P1 网络/环境 | 必要时补可信 Feed 端点及 Windows Python 查找 | 安全边界测试、Python 解析 smoke 通过 |
| P2 消费端 | contracts、来源 UI、Feed 规范化、准入、元数据/初审适配 | 离线样本完整通过，普通 RSS 无回归 |
| P3 端到端 | 三账号试运行、测试 AI、测试归档/通知、文档 | 观察期和交付证据齐全 |
| P4 PR | 整理有界提交、部署说明和限制 | 向上游描述清楚支持范围及实测条件 |

PR 应围绕“通过 RSS 接入 X 帖子”组织，避免混入调度恢复、多用户权限等改造。内部项目分析文件是否随最终 PR 提交，在整理 PR 时决定。

## 数据迁移与回滚

新字段默认 article/空元数据，历史正文保持原样，不回填或重新初审全部资料。只给新建验证源启用 x_post；变更普通源模式需显式操作。

回滚先停用 X 来源、等待在途任务结束，再回退应用；新增列暂保留以免丢失元数据。原版本可能无法正确处理已有 X 内容，因此不能只回退代码却继续启用 X 源。测试数据使用独立 OPENLORE_DATA_DIR，生产回滚不删除文章或 Git 归档。

## 待确定事项

真实账号名单、RSSHub 部署位置和凭据方式在 P0 前确定。完整线程、自动研究外链与删除/编辑同步如有明确需求，应另行评估；当前设计不把它们算进首版完成标准。
