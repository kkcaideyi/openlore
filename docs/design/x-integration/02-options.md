# X 接入方案比较

2026-10-24 补充评估与统一交接入口见 [AGENT-HANDOFF.md](AGENT-HANDOFF.md)。以下为 RSS 专项方案的比较基础；Python 直连已升级为值得共同验证的正式候选，尚未最终选型。

依据：[上下文](01-context-brief.md)。优先级依次为可持续取数、复用现有链路、PR 易维护、部署与凭据成本。

| 方案 | OpenLore 改动 | 运维依赖 | 评价 |
| --- | --- | --- | --- |
| A. RSSHub 输出 RSS，OpenLore 增加明确的 X 帖子模式 | 中：复用 Feed 抓取，补准入/身份/日期/初审适配 | 一个独立 RSSHub 实例及其凭据 | 推荐；账号取数与内容处理边界清楚 |
| B. twscrape/Twikit 加自写 RSS 输出服务 | 中：可复用 A 的消费端 | 自己维护采集、登录会话、游标、XML 输出 | A 取数失败后的候选；新增桥接程序不能算零成本 |
| C. 把 X 爬虫直接接入 Python worker | 较大：新增网络协议、凭据、状态、重试与来源配置 | 爬虫升级与主应用耦合 | 首版不优先；Python worker 当前主要是文件解析器 |
| C2. 独立 Python 采集操作 + Node X adapter | 中：新增来源/采集协议，复用内容池与 Python 环境 | 自己管理会话、限流、增量水位；无需 RSS 服务 | 与 A 做同条件 POC，直连优先验证 twscrape |
| D. 原生 X 官方 API 适配器 | 中—大：新适配器、分页/配额/凭据管理 | 接口权限和当前费用 | 若团队已有 API 配额可以优先复评；本次不提供未核实价格 |

## 推荐与改变选型的条件

先用固定版本 RSSHub 验证指定账号 Feed，再实现供应商无关的 X RSS 消费逻辑。RSSHub 不作为 OpenLore 强制依赖，X 凭据留在中间服务，OpenLore 只消费受配置的 Feed。

补充结论：不必等 RSSHub 完全失败才评估直连。若只服务 OpenLore，可直接验证 C2，省去 B 的 RSS 转换与缓存服务。若团队已有可靠 RSSHub，A 更便于复用。如果团队已有官方 API 权限，则同时比较 RSSHub 的开发者 API 模式与 D 的维护成本。

**只加界面来源按钮不足以完成接入。** 当前日期核验、摘要判定、80 字符阈值、标题与正文相同的初审判断都可能阻断 X 帖子。

## 估算

以下为单人开发的粗估，不含等待凭据、网络/账号问题和上游 PR 评审：取数验证 0.5～1 人日，消费端适配 2～3 人日，测试/文档 1～2 人日；内网安全配置和 Windows 启动兼容若需要，再预留 1～2 人日。真实稳定性观察建议至少 48 小时，与开发并行。不是承诺工期。
